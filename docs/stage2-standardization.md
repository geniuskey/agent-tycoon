# 2단계 표준화 — 미션 설계안 (검토용)

> 상태: 설계 확정, 구현 중. 시나리오 id(가칭) `s2-standardization`

## 한 줄 요약

1단계에서 디지털화한 데이터를 합쳐 보려는데 **같은 설비·같은 시각·같은 "수율"이 시스템마다 다르다.**
AI 어시스턴트로 불일치를 찾게 하고, 부서마다 다른 이해관계를 **사전 조율 → 합의 회의**로 풀어
**표준을 사내 위키에 게시**한다. 이 위키가 이후 단계에서 Agent가 읽는 첫 번째 "지식"이 된다.

## 왜 이 단계가 필요한가 (캠페인 안의 위치)

- 0단계: 데이터가 어디 있는지 안다 → 1단계: 데이터로 만든다 → **2단계: 데이터끼리 말이 통하게 한다**
- 7단계 자유 플레이의 함정 두 개가 여기서 근본 원인으로 등장한다
  - Fab 대시보드 미션의 **UTC/KST 시간대 버그**
  - DRAM 미션의 **단위·명칭 불일치**
- 표준은 기술 문제처럼 보이지만 실제로는 **누가 무엇을 바꾸느냐의 협상**이다. AI가 대신해 줄 수 없는 부분이 핵심이다.

## 학습 목표

1. 데이터 불일치를 AI에게 찾게 하되, **자동 매칭 결과를 그대로 믿지 않는다** (오매칭 검증)
2. "하나로 통일"이 아니라 **기준 키 + 별칭(alias)** 같은, 각자의 업무를 덜 바꾸는 표준을 고른다
3. 입장(position) 뒤의 **이해관계(interest)** 를 1:1로 먼저 파악한 뒤 회의에 들어간다 (사전 조율)
4. 합의한 표준을 **사람과 AI가 모두 읽을 수 있는 문서**(위키)로 남긴다
5. 같은 말이 다른 뜻인 지표(수율)는 **이름을 나눠 정의**한다

## 업무 구조 (업무 보드)

```
단계 1  [match]   데이터 대조: 세 시스템의 설비명·시각·지표 불일치 찾기          (assistant)
단계 2  [draft]   표준 초안: 설비 ID · 시각 · 불량 코드 · 수율 정의               (assistant, 판단 2곳)
        [align]   사전 조율: 부서별 1:1 대화로 이해관계 파악                    (플레이어 — 메신저)
단계 3  [meeting] 합의 회의: 그룹 대화방에서 안건별 합의                        (플레이어 — 메신저)
단계 4  [wiki]    위키 게시: 합의된 표준을 sim://wiki 에 게시                   (assistant, 검토)
단계 5  [apply]   표준 적용: curated 데이터에 표준을 적용하고 주간 지표 재계산       (assistant)
```

`align`은 Agent 업무가 아니라 **사람 업무**다. 업무 보드에 "담당: 나"로 표시되어 Agent에게 맡길 수 없다는 것을 보여준다.

## 함정과 판단 지점

| 위치 | 장면 | 좋은 판단 | 그럴듯한 나쁜 판단 |
|---|---|---|---|
| match | AI가 이름 유사도로 설비를 자동 매칭 — **ETCH-01(2라인 1번)을 "2라인 식각 7호기"와 잘못 묶음** (오매칭 1건) | 매칭표를 열어 확인 후 수정 지시 | 신뢰도 95%라니 그대로 진행 |
| match | 다운타임 메일 시각이 MES보다 정확히 9시간 빠름 | "시간대 차이(UTC)"로 기록 | 메일 시각이 틀렸다고 보고 MES로 덮어쓰기 |
| draft | 설비 명칭 표준 방식 | MES ID 기준 키 + 별칭 표 | 전 부서 ETCH-07로 통일 / AI가 새 체계 제안 |
| draft | 수율 정의 | 두 지표로 나눠 정의 | 수율팀 정의로 통일 (생산 KPI 무시) |
| align | 사전 조율 없이 회의 소집 | 1:1로 이해관계 먼저 확인 | 바로 회의에서 초안 통보 |
| meeting | 안건별 제안 | 이해관계를 반영한 해법 제시 | "팀장님 지시입니다" (압박 → 신뢰 하락, 결렬) |
| wiki | 도구 실행 승인: `wiki.publish(space: 전사 공개)` | 보안 검토 후 "사내 공개 + 데이터 링크 제외"로 게시 | 원본 데이터 경로·공용 계정까지 포함해 전사 공개 |
| apply | 표준 적용 후 주간 지표가 지난주와 다름 | 정의 변경에 따른 차이로 설명 + 과거치 재계산 | "수율이 0.8%p 올랐다"고 보고 |

## 새 메커니즘

### 1) 그룹 대화방 (합의 회의)

메신저에 **그룹 대화방**을 추가한다. 회의는 고정 일정(예: 14:00–14:40)에 열리고, 그 시간에만 안건을 올릴 수 있다.

- 안건(설비 ID / 시각 / 불량 코드 / 수율 정의)마다 플레이어가 **제안 하나**를 고른다
- 참석자는 각자 반응한다: 이해관계가 반영됐고(`interest.*` 플래그) 신뢰가 충분하면 **동의**, 아니면 **반대 + 이유**
- 반대가 남은 안건은 **보류**. 회의 후 1:1로 다시 조율하고 다음 회의(내일 10:00)에 재상정할 수 있다
- 모든 안건이 합의되면 참석자 **서명(✔)** → 팀장 승인 가능

데이터 모델 (초안):

```jsonc
"groups": [{
  "id": "std-meeting", "name": "표준 합의 회의",
  "members": ["oh", "seo", "kang", "choi", "lee", "han"],
  "schedule": [{ "from": "14:00", "to": "14:40" }, { "from": "D+1 10:00", "to": "10:40" }],
  "agenda": [{
    "id": "equip-id", "title": "설비 명칭 표준",
    "proposals": [{
      "id": "mes-key-alias", "label": "MES ID를 기준 키로, ETCH-07 등은 별칭으로 공식 인정",
      "reactions": [
        { "member": "oh", "when": "interest.oh", "agree": true, "say": ["별칭으로 남는다면 저희는 바꿀 게 없네요. 동의합니다."] },
        { "member": "oh", "agree": false, "say": ["결국 우리 보고 바꾸라는 거 아닙니까?"] }
      ],
      "quality": "good"
    }]
  }]
}]
```

### 2) 사내 위키 (`sim://wiki`)

- 가상 브라우저의 사내 페이지로 추가 (업무 보드와 같은 방식)
- 2단계에서 만드는 문서: `표준/설비 ID`, `표준/시각`, `표준/불량 코드`, `표준/지표 정의`
- 문서마다 **소유 부서, 개정 이력, 합의 서명**이 붙는다
- 이후 단계와의 연결
  - 3단계(데이터 기반): 스키마가 위키 표준을 참조
  - 4단계(지식화): 위키가 Agent가 읽는 지식의 중심이 된다 (CLAUDE.md·스킬로 확장)
  - 5–6단계: Agent 설정에서 "읽을 수 있는 위키 공간"을 권한으로 고른다

### 3) 사람이 맡는 업무

Task에 `owner: "player"`를 두면 업무 보드에 "담당: 나"로 보이고 Agent 지시 선택지에서 빠진다. 완료 조건은 플래그(예: 이해관계 4개 중 3개 파악)로 판정한다.

## 평가 (기존 9개 차원 + 협업)

| 차원 | 이 미션에서 보는 것 |
|---|---|
| 검증 | 자동 매칭표를 열어보고 오매칭을 고쳤는가 |
| 도메인 | 시간대 차이를 오류가 아닌 표기 차이로 해석했는가, 수율 정의를 나눴는가 |
| 이해관계자 협업 | 사전 조율을 했는가, 회의에서 압박 없이 합의했는가, 서명 수 |
| 보안 | 위키 공개 범위·데이터 링크 처리 |
| 근거 | 지표 변동을 정의 변경으로 설명했는가 |

요청자 반응은 합의 수준에 따라 갈린다: **전원 서명** / 일부 보류(조건부 승인) / 결렬(재작업)
