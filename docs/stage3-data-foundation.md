# 3단계 데이터 기반 구축 — 미션 설계안 (검토용)

> **단순화 (기능 사다리):** 이 단계는 새 기능 하나에 집중한다. 운영 정책 확인·카탈로그·데이터 오너 승인·운영 이관과 윤하린·이도윤·한유진, 문서 Agent는 뺐다. 마트 안내 위키는 권한 설계가 함께 쓴다. Agent는 data-engineer·quality 두 개. 아래 설계 중 이 부분은 현재 시나리오에 없다.

> 상태: 설계 확정, 구현 중. 시나리오 id(가칭) `s3-data-foundation`

## 한 줄 요약

2단계 위키 표준을 바탕으로 **수율 데이터 마트**를 만든다: 데이터 모델 → 적재 파이프라인 → 품질 규칙 → 접근 권한 → 데이터 카탈로그.
처음으로 **역할이 다른 Agent 여러 개**(데이터 엔지니어·품질 검증·문서)를 나눠 쓰고, 플레이어는 **조정자**로서
IT 운영 정책과 데이터 오너의 승인을 받아낸다. 결과물은 4단계 이후 **AI가 조회하는 단일 출처**가 된다.

## 캠페인 안의 위치

- 1단계: 데이터를 만든다 → 2단계: 말이 통하게 한다 → **3단계: 믿고 꺼내 쓸 수 있게 쌓는다**
- 앞 단계에서 놓친 것이 여기서 **데이터 사고**로 터진다 (아래 '이월 효과')
- 5–6단계 Agent 설계의 예고편: AI 어시스턴트에게 **어떤 데이터를 어떤 권한으로** 줄지 처음 정한다

## 학습 목표

1. 저장 단위(입도)와 기준 키를 먼저 정한다 — 집계만 저장하면 원인 분석을 못 한다
2. 운영 시스템의 정책(운영 DB 직접 조회 금지, 야간 배치 창)을 존중해 적재 방식을 고른다
3. 품질 규칙이 **'모른다'는 정직한 표시**(LOW_CONFIDENCE, NOT_MEASURED)를 오류로 버리지 않게 한다
4. 실패한 데이터를 조용히 버리지 않는다 — 격리하고 알린다
5. AI도 사람처럼 **최소 권한**: 마트 읽기 전용, 원천·가명 매핑 키는 제외
6. 업무를 역할별 Agent에게 나누고, 서로 기다리지 않는 일은 동시에 맡긴다

## Agent (처음으로 여러 역할)

| 역할 | 하는 일 | 못 하는 일 |
|---|---|---|
| data-engineer | 데이터 모델, 적재 파이프라인, 첫 적재 실행 | 다른 부서 승인 받기 |
| quality | 품질 규칙 제안·검증 실행 | 규칙의 업무적 의미 판단 (현장 표기 등) |
| assistant | 데이터 카탈로그·위키 문서 | 데이터 처리 |

## 업무 구조

```
단계 1  [model]     데이터 모델 설계 — 입도·기준 키·시각 필드            (data-engineer, 판단 2)
단계 2  [pipeline]  적재 파이프라인 — 소스·일정·실패 처리               (data-engineer, 판단 2)   ‖
        [rules]     품질 규칙 정의                                    (quality, 판단 1: 복수 선택) ‖ 병렬
        [policy]    IT·플랫폼 운영 정책 확인                           (나 — 메신저)
단계 3  [load]      첫 적재 실행 + 품질 검증                           (data-engineer → quality)
단계 4  [access]    접근 권한 설계 + 데이터 오너 승인                   (나 + data-engineer, 도구 승인 1)
        [catalog]   데이터 카탈로그 위키 등록                           (assistant)               ‖ 병렬
단계 5  [handover]  운영 이관 승인                                     (나 — 윤하린 책임)
```

## 판단 지점

| 위치 | 장면 | 좋은 판단 | 그럴듯한 나쁜 판단 |
|---|---|---|---|
| model | 저장 단위 | 설비 × 이벤트(시각) 단위로 저장, 주간 지표는 뷰로 계산 | 주간 집계만 저장 ("용량 절약") |
| model | 설비 키 | 기준 키 `eq_id` + 별칭 차원 테이블 | 부서별 이름 텍스트 그대로 저장 |
| pipeline | 소스 | IT가 제공하는 일 배치 export (02–04시 창) | 운영 MES DB 실시간 직접 조회 (도구 승인: `Bash(psql -h mes-prod-db …)`) |
| pipeline | 실패 행 처리 | 격리 테이블 + 담당자 알림 | 조용히 건너뛰기 / 전체 적재 중단 |
| rules | 품질 규칙 (복수) | 키 무결성(별칭 미등록 = 실패), 중복, 미래 시각, **LOW_CONFIDENCE·NOT_MEASURED는 허용** | "결측 0% 강제", AI가 제안한 일반 규칙 40개 전부 |
| load | 품질 리포트 | 실패 건의 원인을 찾아 해당 오너에게 확인 | 경고 무시하고 마트 공개 |
| access | AI 어시스턴트 권한 (도구 승인: `grant(ai-assistant, raw.* + mart.*, read/write)`) | 마트 읽기 전용, 원천·가명 매핑 키 제외 | 요청대로 전체 권한 |
| access | 데이터 오너 승인 | 오너별 조건(별칭 유지·이력 보존·매핑 키 분리)을 확인하고 1:1로 승인 | 팀장 명의로 일괄 승인 요청 |

## 이월 효과 — 앞에서 놓친 것이 터지는 곳

| 앞 단계 상태 | 3단계에서 |
|---|---|
| 2단계 설비 ID 합의 실패 (별칭 표 없음) | 첫 적재에서 설비팀 데이터 38%가 조인 실패 → 오태식 파트장에게 다시 협의해야 함 |
| 2단계 자동 매칭 오류(`match.auto`) | 키 무결성 규칙을 넣었으면 "2라인 정지가 3라인 설비에 연결" 탐지, 안 넣었으면 **조용히 틀린 마트** |
| 2단계 시각 덮어쓰기(`time.overwrite`) | 중복·미래 시각 규칙에 걸림 |
| 1단계 판독 불가 셀(LOW_CONFIDENCE) | "결측 0%" 규칙을 고르면 정직하게 비워 둔 행이 버려짐 |
| 2단계 위키 전사 공개 | 한유진 책임 신뢰 하락 → 권한 승인 조건이 더 까다로움 |

## 다음 단계로 넘기는 것

- 마트 구조와 카탈로그 (`/wiki/data/*.md`) → 4단계 지식화에서 Agent가 읽는 데이터 지식
- AI 어시스턴트 권한 범위 (`access.ai.*`) → 5단계 단일 Agent 활용의 시작 조건
- 품질 규칙 → 이후 단계 Agent 결과 검증의 기준

## 결정 사항 (2026-11-23)

1. 데이터 콘솔: **내장 뷰** — 페이지 `view: "db"`가 줄 단위 콘솔 파일(`table|…`, `check|…`, `quarantine|…`, `grant|…`)을 표로 보여준다
2. Agent: **역할 3개** (data-engineer · quality · assistant)
3. 데이터 오너 승인: **1:1 메신저**로 오너별 조건을 확인하고 각각 승인
