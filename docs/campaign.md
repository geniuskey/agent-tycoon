# 캠페인 설계 — "AI가 일할 수 있는 조직을 만든다"

## 왜 재설계했나

초기 버전은 "Agent가 이미 있고, 데이터는 정리돼 있고, 권한도 있다"는 전제 위에서 멀티 Agent 오케스트레이션을 체험했다.
그러나 실제 현장의 출발점은 다르다.

- 데이터가 **종이 체크시트, 주마다 양식이 바뀌는 엑셀, 메일 본문, 개인 매크로, 사람 머릿속**에 흩어져 있다
- 같은 설비·불량을 부서마다 다른 이름·코드·단위·시간대로 기록한다 (표준화 부재)
- 데이터를 만드는 사람(현장)·쓰는 사람(실무)·지키는 사람(보안)의 이해관계가 다르다

AI Agent는 **앞 단계에서 만든 기반만큼만** 일할 수 있다. 그래서 체험도 그 순서를 따른다.

## 단계 구성

| 단계 | 이름 | 플레이어 | 핵심 체험 | 상태 |
|---|---|---|---|---|
| 0 | 현황 파악 | 실무자 | 인터뷰로 데이터 출처·숨은 규칙·품질 리스크·보안 요건 파악, 계획 승인 | ✅ `s0-data-discovery` |
| 1 | 디지털화 | 실무자 | 종이·엑셀 → 구조화 데이터, AI(OCR) 결과 검증, 불확실성 표시, 개인정보 | ✅ `s1-digitization` |
| 2 | 표준화 | 실무자 → 조정자 | 명칭·코드·단위·시간대 기준을 **부서 간 협의**로 합의 | 준비 중 |
| 3 | 데이터 기반 구축 | 조정자 | 스키마, 적재, 품질 규칙, 권한, 이력 | 준비 중 |
| 4 | 지식화 | 조정자 | SOP·숨은 규칙·노하우를 AI가 참고할 지식으로 | 준비 중 |
| 5 | 단일 Agent 활용 | 리더 | Agent 하나에 위임·검증 | 준비 중 |
| 6 | Agent 설계 | 리더 | 업무 선정, 도구·권한·평가 기준 | 준비 중 |
| 7 | 멀티 Agent 오케스트레이션 | 리더 | 기존 3개 미션 (DRAM, Fab 대시보드, 회의 요약) — 자유 플레이 | ✅ |

플레이어 역할은 **실무자 → 조정자 → 리더**로 옮겨간다. 초기에는 AI 어시스턴트 하나를 보조로 직접 일하고(사람을 만나는 건 AI가 대신 못 한다), 후반으로 갈수록 위임과 설계 비중이 커진다.

## 단계 간 이월 (Carry-over)

한 미션을 제출하면 `exportCarry()`가 회사 상태를 만들어 다음 미션의 시작 상태로 넘긴다.

| 이월 항목 | 예시 | 다음 단계에서의 효과 |
|---|---|---|
| 파악한 사실 (flag) | `found.legend` (현장 기호 X=NG) | 1단계 OCR이 기호를 처음부터 올바르게 해석 |
| | `found.code_rule` (구 D07 처리 기준) | 1단계 코드 매핑 질문 없이 처리 |
| 산출물 (file) | 인벤토리, 계획, 숨은 계산 규칙 문서 | 다음 미션의 가상 파일로 존재 |
| 신뢰도 | 최재석 반장 65 | 1단계에서 판독 불가 셀 확인 요청에 응함 (minTrust 45) |

0단계에서 현장을 "태블릿으로 입력하라"고 압박해 신뢰를 잃으면, 1단계에서 반장이 기호의 뜻도, 번진 숫자도 알려주지 않는다. **놓친 것은 다음 단계에서 문제로 돌아온다.**

- 시나리오 정의: `campaign.carry = { flags: [접두어...], files: [...], trust: true }`
- 선행 미션 없이 시작: `campaign.defaultCarry` (홈에서 "이전 단계 먼저 (기본값으로 시작 가능)")
- 세션 기록에 `carry`(받은 상태)와 `exportCarry`(넘긴 상태)를 함께 저장 → 재생·복기 결정성 유지

## 가상 인물 (협의 시뮬레이션)

```jsonc
"people": [{
  "id": "choi", "name": "최재석 반장", "trust": 30,
  "greeting": [...], "fallback": [...], "rude": [...],
  "topics": [
    { "id": "pain", "patterns": ["불편", "힘든"], "trust": 15, "hint": "현장에서 불편한 점이 있으세요?", "reply": [...] },
    { "id": "backfill", "patterns": ["언제\\s*적"], "minTrust": 50, "lowTrust": ["그때그때 적죠."], "reply": [...],
      "effects": [{ "type": "setFlag", "flag": "found.backfill" }] }
  ]
}]
```

- **신뢰도(0–100)**: 질문 방식에 따라 변한다. 상대의 부담을 묻고(pain), 걱정을 덜어주고(reassure), 약속하면 오른다. 압박·무례(당장, 내놔…)나 상대를 대체하겠다는 말은 깎인다.
- **minTrust**: 중요한 정보(숨은 매크로 규칙, 사후 기록 관행)는 신뢰가 쌓여야 털어놓는다. 부족하면 얼버무린다(`lowTrust`).
- **조건부 주제**: `requires`로 상황에 따라 다른 반응 (예: 팀장은 계획에 보안 검토가 빠지면 승인하지 않음, 빅뱅 계획은 반려).
- **알 수 없는 질문**: 성공 처리하지 않고 인물답게 되묻고, 물어볼 만한 질문 예시를 보여준다.
- 대화는 사내 메신저(오른쪽 탭, `talk <id>`로도 열림)에서 한다. 메시지는 비동기로, 상대가 읽을 때(`replyDelay`, `schedule` 회의 일정) 답이 온다.
- 평가에 **이해관계자 협업** 차원이 추가된다 (만난 사람, 신뢰 변화, 무례, 대답 회피).

## 다음 구현 후보: 2단계 표준화

부서 간 합의 시뮬레이션이 본격적으로 필요한 단계다.

- 같은 설비를 생산(“2라인 7번 식각기”)·설비(`ETCH-07`)·MES(`EQ-N2-ET07`)가 다르게 부른다
- 시간대: 설비 로거 UTC vs MES KST (7단계 Fab 대시보드 미션의 함정이 여기서 근본 해결)
- 불량 코드 개정 매핑의 공식화, 단위(ms/s) 표기 규칙 (7단계 DRAM 미션의 함정)
- 협의 메커니즘 확장 아이디어: 다자 회의(여러 인물 동시), 입장(position)과 이해관계(interest) 구분, 양보·교환 제안, 합의안 문서 서명
